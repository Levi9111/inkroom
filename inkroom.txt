## 1. Executive Summary

The initial plan (React + TypeScript, Konva, Yjs, Node, PostgreSQL/Redis, five phases) is a **sound starting point**. The technology choices are mainstream and the feature list covers the basics. However, the audit found **18 findings**: 4 critical, 7 major, 7 minor. The most important are:

- **Undo/redo is designed to conflict with collaboration.** A global Zustand history stack will undo other people's edits once Yjs is the source of truth.
- **The plan never decides between building and integrating** (fork Excalidraw, use the tldraw SDK, or build on Konva). That choice drives the timeline, license and product identity.
- **Pen quality and rendering performance are under-specified.** For a classroom product, the feel of writing with a stylus is the product. Konva's per-node model will also slow down with thousands of strokes.
- **Classroom-specific requirements are missing or deferred**: roles and permissions, PDF/slide annotation, multi-page boards, privacy for minors, moderation, offline resilience, accessibility and multi-script text input.
- **The timeline is unrealistic** (8 weeks for a collaborative whiteboard), and the infrastructure is heavier than an MVP needs (Redis, separate presence store).

**Final recommendation in one paragraph:** Build a **local-first, single-user whiteboard first**, then add collaboration. Use **React (UI chrome only) + imperative Konva (canvas) + `perfect-freehand`** for rendering, a **spatial index (rbush)** for culling and hit-testing, and **Yjs with one document per page** served by **Hocuspocus** for sync and per-page permissions. Follow the **MERN stack with TypeScript end to end**: **Express on Node.js** hosts both the REST API and Hocuspocus, and **MongoDB** (via Mongoose) stores board metadata and the binary Yjs state, with images and PDF pages in S3-compatible storage (or local disk when self-hosting). The one MERN-specific hazard is MongoDB's 16 MB document limit, handled in Section 6.6.4. Make **teacher/student roles, PDF annotation, multiple pages, and privacy-by-default** core features, not extras. License under **MIT**. Plan for roughly **8 months** at part-time pace, with a usable public alpha at about month 3.

## 2. Scope, Method & Assumptions

### 2.1 Scope
This report audits the supplied research/plan document and produces a replacement plan. It does not audit any existing codebase (none exists yet).

### 2.2 Method
- Reviewed every claim and recommendation in the original document for correctness, completeness, feasibility and risk.
- Cross-checked the architecture against known constraints of Yjs/CRDTs, canvas rendering, pointer-input handling, and web security.
- Classified findings by severity:
  - **Critical**: will cause rework or product failure if not fixed.
  - **Major**: significant quality, cost or schedule impact.
  - **Minor**: improvement or hygiene item.

### 2.3 Assumptions
- Solo developer, working part-time (about 10 to 15 hours per week). Timelines scale accordingly.
- Target users: teachers and students from primary school through university, on mixed devices (laptops, Chromebooks, tablets with stylus, phones as secondary), often with unreliable internet.
- "Free" means no paywalled core features and a simple self-host path, not unlimited free hosting.
- Existing third-party projects named in the original document (FalconBoard, Boardier, Tapiz, GalleryBoard, etc.) were **not independently verified** here. Check their repositories and licenses yourself before borrowing ideas or code.

### 3.3 What the Initial Plan Got Right
- Yjs (CRDT) for collaboration, which is more robust than hand-rolled OT or last-write-wins.
- TypeScript throughout; Zustand for UI state; Tailwind for speed.
- Room-code join flow modeled on classroom-friendly tools.
- Separation of client, collaboration server and persistence.
- Studying Excalidraw's monorepo structure and core/app separation.

## 4. Product Definition

### 4.1 Vision
> A whiteboard that a teacher can open and start teaching on within 30 seconds, that a student can join without an account, and that anyone can host for free.

### 4.2 Personas

| Persona | Needs | Constraints |
|---|---|---|
| **Teacher (primary)** | Fast start, natural writing, annotate slides/PDFs, control who can draw, save/export the lesson | Often on a projector, mixed devices, little time |
| **Student** | Join by code, write/draw when allowed, see the board clearly | May be a child; shared or low-end device; no email |
| **Tutor / freelance instructor** | Quick one-to-one sessions, math tools | Often on a tablet with a stylus |
| **School IT / self-hoster** | One-command install, no vendor lock-in, privacy control | Limited budget and time |

### 4.3 Goals
1. Writing with a stylus or mouse feels as good as the best commercial tools.
2. Real-time collaboration that survives bad networks.
3. Teacher-first controls (roles, permission modes, moderation).
4. Zero-friction student access, with privacy by default.
5. Trivial self-hosting; fully open source.

### 4.4 Non-Goals (v1)
- Video/audio conferencing and screen sharing
- Built-in chat (a minimal reactions/raise-hand mechanism instead)
- Handwriting-to-text recognition
- LMS integration (LTI) and gradebooks (consider post-v1)
- Native mobile apps (the PWA covers tablets and phones)

### 4.5 Design Principles
1. **Canvas first**: chrome stays out of the way; the board is at least 90% of the screen.
2. **Big and legible**: projector-readable defaults, large touch targets.
3. **Predictable**: every action is undoable; destructive actions are confirmable.
4. **Resilient**: never lose work; always show connection state honestly.
5. **Private by default**: collect nothing you don't need.

### 4.6 Name & Brand

**Name: Inkroom**
- **Why it fits**: "Ink" is the core interaction (writing and drawing), and "room" matches the product's model: every session is a room you join with a code. It is short, easy to spell and say, and works in many languages' keyboards and scripts for URLs.
- **Tagline**: *Write together. Teach anywhere.*
- **One-line description**: "Inkroom is a free, open-source whiteboard for classrooms: open it, share a code, and start teaching."
- **Voice**: friendly, plain-spoken, teacher-first; no jargon, no growth-hacking.
- **Identifiers (proposed)**: GitHub org `inkroom`, npm scope `@inkroom`, packages `@inkroom/core`, `@inkroom/ui`, `@inkroom/shared`, Docker image `ghcr.io/<org>/inkroom`, file extension `.inkroom`.
- **Visual identity direction**: a rounded speech-bubble/room outline containing a single pen stroke; primary color indigo (`#4F46E5`, matching the accent token), with a chalk-white variant for dark and blackboard themes. Wordmark in the UI font (Inter, semi-bold, tight tracking).

**Availability checklist (do before announcing publicly)**
1. Domain: check `.org`, `.app`, `.io` and a short country-code option. Prefer `.org` or `.app` for an open-source project.
2. Registries and hosts: npm package and scope, GitHub org/repo, and Docker Hub/GHCR.
3. Social handles: GitHub, X, LinkedIn page, YouTube, Mastodon/Bluesky.
4. Trademark: search the relevant registries (e.g. USPTO, EUIPO, WIPO Global Brand Database) for "Inkroom" and close variants in software and education classes. A quick web search found other whiteboard products with similar-sounding names (for example Inko, an iPad whiteboard app), so confirm there is no confusing overlap before committing.
5. Search-engine test: confirm the name is not dominated by an unrelated, higher-ranking brand.

**Fallback names (same direction, in order of preference)**: **Chalkroom**, **Slateroom**, **Penroom**, **Inkboard**, **Boardwise**. Re-run the checklist for whichever you choose; any name is only final after the trademark check passes.

### 6.3 Rendering Pipeline

1. **Input**: Pointer Events (`pointerdown/move/up`) with `getCoalescedEvents()` for full stylus fidelity; `touch-action: none` on the canvas; ignore `pointerType === 'touch'` for ink when a pen is active (palm rejection), and let touch pan/zoom.
2. **Live ink**: the in-progress stroke renders on the **active layer** only. Points are throttled (about 30 to 60 ms) into Awareness as a draft so peers see ink forming, without writing partial data into the CRDT.
3. **Commit**: on `pointerup`, simplify points (Ramer–Douglas–Peucker, epsilon scaled by zoom), then insert **one** element into the page doc inside a transaction with the local origin.
4. **Static layer**: committed elements are rendered through a viewport-culled pass using the **rbush** index; stroke outlines from `perfect-freehand` are cached per element (`Path2D`) and invalidated only on change. When element count is large, rasterize unchanged regions into cached bitmaps.
5. **Hit-testing and selection**: use rbush for broad-phase and custom distance-to-polyline tests for strokes (Konva's hit graph is too costly for thousands of strokes).
6. **Eraser**: stroke eraser deletes whole elements intersecting the eraser path (a soft preview highlights what will be removed). Partial erase (splitting strokes) is a post-v1 enhancement.

### 6.4 Collaboration & Sync

- **Documents**: `board:<id>:meta` (title, mode, page list) and `board:<id>:page:<pageId>` (elements). Hocuspocus multiplexes documents over a single WebSocket.
- **Presence**: Yjs Awareness carries cursor position, display name, color, current tool, live draft stroke, laser trail, raised-hand flag, and viewport (for follow mode).
- **Undo**: `Y.UndoManager` per page doc, with `trackedOrigins` set to the local user origin. Remote changes are never on the local undo stack.
- **Offline**: `y-indexeddb` stores each doc locally; on reconnect, Yjs merges automatically. The UI shows connection state honestly (Section 9.6).
- **Persistence**: Hocuspocus's database extension stores the binary Yjs state in MongoDB (debounced, e.g. 2 s after the last change, max 10 s; storage strategy in 6.6.4). Periodic **restore points** (snapshots) enable teacher "restore earlier version".
- **Garbage collection**: keep Yjs GC enabled; compact stored state on a schedule.

### 6.5 Roles, Permissions & Trust Model

**Roles**: `teacher` (full control), `co-teacher` (teacher-equivalent, revocable), `student`, `viewer` (read-only link).

**Identity and tokens**
- Creating a board returns a **teacher secret** placed in the URL **fragment** (`/t/<boardId>#<secret>`) so it never reaches server logs.
- Students join with a short **room code** (`/b/<code>`, 8 characters, unambiguous alphabet, rate limited).
- The server exchanges either for a short-lived **JWT** carrying `boardId`, `role`, `participantId`, and display name.

**Board modes** (switchable live by a teacher):

| Mode | Students can | Use |
|---|---|---|
| **Present** | View only, follow the teacher's view | Lecturing |
| **Collaborate** | Draw/edit on shared pages (within limits) | Group work |
| **Individual** | Draw only on their own private page; teacher sees all | Exercises, tests |
| **Locked** | View only, nobody can edit | Freeze the board |

**Enforcement (be honest about limits)**
- Yjs updates are opaque to the server, so **fine-grained rules cannot be fully enforced server-side**. The practical model is:
  1. **Connection/document-level** enforcement in Hocuspocus: view-only students get read-only connections; in Individual mode each student's write access is limited to their own page document.
  2. **Client-level** soft rules (e.g. students can only edit their own elements) for UX.
  3. **Safety nets**: server-side size/rate limits, author attribution on every element, one-click "remove all strokes by this participant", and restore points.
- Verify during Spike S-2 that connection read-only state can be changed at runtime when a teacher switches modes. If not, fall back to reconnecting clients with a new token.

#### 6.6.3 Bootstrap (Express + Hocuspocus on one server)

```ts
// apps/server/src/index.ts
import http from 'node:http';
import express from 'express';
import helmet from 'helmet';
import { WebSocketServer } from 'ws';
import { Hocuspocus } from '@hocuspocus/server';
import { Database } from '@hocuspocus/extension-database';

const app = express();
app.use(helmet());
app.use(express.json({ limit: '100kb' }));

const server = http.createServer(app);
const wss = new WebSocketServer({ noServer: true });

const hocuspocus = new Hocuspocus({
  async onAuthenticate({ token, documentName, connectionConfig }) {
    const claims = await verifyJwt(token);
    if (!canAccess(claims, documentName)) throw new Error('forbidden');
    connectionConfig.readOnly = !canWrite(claims, documentName);
    return { user: { id: claims.participantId, role: claims.role } };
  },
  extensions: [
    new Database({
      fetch: async ({ documentName }) => loadYState(documentName),
      store: async ({ documentName, state }) => saveYState(documentName, state),
    }),
  ],
});

server.on('upgrade', (req, socket, head) => {
  if (!isAllowedOrigin(req)) return socket.destroy();
  wss.handleUpgrade(req, socket, head, (ws) => hocuspocus.handleConnection(ws, req));
});

server.listen(8080);
```

| `ydocs` | `_id` = document name (`board:<id>:meta` or `board:<id>:page:<pageId>`), `boardId`, `state` (Binary), `bytes`, `updatedAt` | index on `boardId` |

## 13. DevOps, Deployment & Self-Hosting

- **CI** (GitHub Actions): lint, typecheck, unit, e2e, build, bundle-size check, accessibility, release notes.
- **Releases**: semantic versioning; Docker images published to GHCR; changelog.
- **Self-host in one command**:
  ```yaml
  services:
    inkroom:
      image: ghcr.io/<org>/inkroom:latest
      ports: ["8080:8080"]
      environment:
        - MONGODB_URI=mongodb://mongo:27017/inkroom
        - ASSET_STORAGE=local
        - JWT_SECRET=${JWT_SECRET}
        - ALLOWED_ORIGINS=https://board.example.org
        - BOARD_RETENTION_DAYS=30
  ```
